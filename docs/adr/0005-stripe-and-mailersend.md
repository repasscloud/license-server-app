# ADR-0005: Stripe and MailerSend integration

- **Status:** Accepted · 2026-10-11

## Stripe

- **The database is the catalogue master.** Offers and price versions are created in PostgreSQL. Changing an amount, currency or interval creates a new price version. Activating it archives the previous version, and existing subscriptions keep their price. (The original design also created an immutable Stripe Price per price version and drift-checked it; that was superseded by the database-only prices decision below.)
- **Prices are database-only (owner decision 2026-10-12).** Checkout line items use inline `price_data` (amount, currency, interval) against one Stripe Product per offer; no Stripe Price objects are created, synced or drift-checked. Fulfilment verifies the charged unit amount, currency, interval and product against the checkout snapshot.
- **Stripe Products: Stripe-first and linked by ID, or created once at first checkout (owner decisions 2026-10-12).** Normally the product (name, description, images shown at Checkout) is created in Stripe by the `stripe-catalogue` script and its `prod_…` ID is linked to the offer (`stripe_product_mappings`, one product per offer, `stripe_product_id UNIQUE`) by the CSV import or `PUT /offers/{id}/stripe-product`. An offer that was never linked (PostgreSQL-first) gets its product created from the database offer at its **first checkout** (`ensureStripeProduct`): the mapping row is locked for the operation (concurrent checkouts wait and reuse it), creation uses the idempotency key `repass-product-<offerId>`, and Stripe is first searched for a product tagged `repass_offer_id` = the offer, which recovers a product whose link write was lost after the idempotency window; two tagged products is a conflict for an administrator. The server never renames, re-describes or archives an existing product; it verifies products and adds `repass_offer_id`/`repass_sku` metadata. Activation requires a linked product to be verified (an unlinked one is created at checkout), and each checkout records the product it was opened against (`checkouts.stripe_product_id`), which fulfilment checks.
- **Catalogue CSV import reports conflicts and never resolves them (owner decision 2026-10-12).** `stripe-catalogue/products.csv` feeds PostgreSQL through a preview → confirmed apply flow (`catalogue_imports`, admin UI and API alike). When the CSV, the database and Stripe disagree on anything the import may not change (a Stripe product's name, description, status or SKU tag; an offer's existing link; what an offer grants; a product, major or edition setting) the row is rejected with both values, and an administrator decides which side is wrong. Apply recomputes the preview and refuses if anything changed since it was reviewed. Prices changed on an offer that is on sale become draft versions for an administrator to activate. See `stripe-catalogue/README-LICENSE-SERVER.md`.
- **API version pinned to `2026-09-30.endive`** (upgraded from `2026-08-26.dahlia` on 2026-10-12, at the owner's request). Every GA breaking change in endive was reviewed against what the code sends and reads: `payment_method_types` removal on Checkout Sessions (never sent; Checkout uses dynamic payment methods); `billing_cycle_anchor` becoming an object (a request parameter we never send); the new `failed_tax_calculation` error code (Checkout creation failures are handled generically, and invoice finalisation errors are not parsed); thin events for v1 resources (opt-in, `v1.`-prefixed; the webhook uses snapshot events, whose shapes are unchanged). The remaining breaking changes are in Connect, Treasury, Financial Connections, SEPA, PayTo, BLIK, Radar evaluations and Stripe.js, none of which are used. The object shapes the code depends on (subscription item periods, `invoice.parent.subscription_details`, Checkout Session, Charge, Dispute, Invoice Payments) are unchanged. Upgrading again means updating `STRIPE_API_VERSION`, the webhook endpoint version, re-reading the changelog, and running a test-mode end-to-end pass.
- **No SDK.** A small fetch adapter handles form encoding, idempotency keys on every POST, timeouts and error classification. Webhook verification is HMAC-SHA256 of `t.rawBody` with a 300-second tolerance, compared in constant time.
- **Checkout** accepts only sku, currency, quantity, email and idempotency key from the browser. Everything else comes from the database. Fulfilment requires verified Stripe state, re-fetched from the API, and checks it against the stored snapshot. `livemode` must match the configured key.
- **Lifecycle events handled:** `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `checkout.session.expired`, `invoice.paid`, `invoice.payment_failed`, `customer.subscription.created`, `.updated`, `.deleted` and `.trial_will_end`, `charge.refunded`, `charge.dispute.created`, `charge.dispute.closed`. Refund and dispute handling follows each component's `refund_action` / `dispute_action` (`revoke` | `review` | `none`). Partial refunds always go to review. A won dispute is flagged and never automatically un-revoked. Cancellation and non-payment never revoke anything.
- **Tax** is opt-in per offer (`automatic_tax`, `tax_id_collection`). This requires **Stripe Tax** to be configured in the Stripe account, including Australian GST registration if applicable. The server does not calculate tax itself. Price versions carry `tax_behavior`.

## MailerSend

- Templates live in `email_templates` (subject, HTML, text, optional MailerSend template ID). `{{var}}` is HTML-escaped; `{{{var}}}` is reserved for server-built fragments.
- The outbox is the only path. Recipients and variables are AES-GCM-encrypted at rest and purged once a message is sent or reaches a terminal state. The `business_key UNIQUE` constraint guarantees one email per business event.
- Retry policy: 429 and 5xx are retried, honouring `Retry-After` and using exponential backoff up to 10 attempts. Other 4xx responses are dead immediately. A timeout means the message *may* have been sent, so the email is marked **`uncertain`** and is not resent automatically. MailerSend documents no idempotency key, so resending could duplicate mail. An operator resolves it from the admin UI.
- The optional delivery webhook is verified with HMAC-SHA256 hex of the raw body (`Signature` header). It updates delivered/bounced state and suppresses hard bounces and complaints. **Without `MAILERSEND_WEBHOOK_SECRET` the endpoint returns 404**, and the UI states that "sent" means *accepted*, not delivered.
- The outbox refuses marketing mail. Marketing requires a separate, consent-based system.
